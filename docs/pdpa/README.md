# PDPA pack — ชุดเอกสารคุ้มครองข้อมูลส่วนบุคคล

สถานะ: **ร่างครบ รอเจ้าของกิจการเติมข้อมูลและให้นักกฎหมายตรวจ** (9 ก.ย. 2026)

เอกสารชุดนี้เขียนจาก **โค้ดจริงของระบบ** ไม่ใช่แม่แบบทั่วไป ทุกข้อที่เขียนว่าระบบทำอะไรถูกตรวจกับ
`schema.prisma` และ module ที่เกี่ยวข้องแล้ว

| ไฟล์ | ใช้ทำอะไร | ใครอ่าน |
|---|---|---|
| `privacy-policy.md` | นโยบายที่ต้องเผยแพร่ให้ลูกค้าอ่าน | ลูกค้า (หลังเติมข้อมูลและตรวจแล้ว) |
| `consent-notices.md` | ข้อความขอความยินยอม + จุดที่ต้องวางในระบบ | คนทำ UI |
| `data-map.md` | เก็บอะไร ที่ไหน นานแค่ไหน ใครเห็น | เจ้าของ + คนดูแลระบบ |
| `data-subject-requests.md` | ขั้นตอนตอบคำขอ ขอดู/ขอแก้/ขอลบ | เจ้าของ + แอดมิน |

> ⚠️ **ผมไม่ใช่นักกฎหมาย** เอกสารนี้เป็นร่างที่ทำให้ทนายตรวจได้เร็วขึ้น ไม่ใช่ตัวแทนการตรวจโดยทนาย
> โดยเฉพาะข้อ "ระยะเวลาเก็บข้อมูล" และ "ฐานทางกฎหมาย" ควรให้ผู้รู้ยืนยัน

---

## ต้องตัดสินใจก่อนเปิดใช้จริง

### 1. ✅ การตลาดเปลี่ยนเป็นขอความยินยอมก่อนแล้ว (ทำตามทางเลือก ข.)

ลงในโค้ดแล้ว (migration 0019) — `canReceiveMarketing()` เป็นแหล่งความจริงเดียว ต้องผ่านทั้ง
"เคยยินยอม" และ "ยังไม่ถอน" · ลูกค้าเดิม backfill เป็น `marketingConsentSource='legacy'`
**จำนวนผู้รับจึงไม่ตกทันที** และจะถูกถามจริงเมื่อเปิดหน้าโปรไฟล์ครั้งถัดไป

**สิ่งที่เจ้าของต้องทำต่อ**: ส่ง broadcast ขอความยินยอม 1 รอบถึงกลุ่ม `legacy`
เพื่อเปลี่ยนความยินยอมให้เป็นของจริง · ถ้าต้องการเข้มกว่านั้น ตั้ง legacy ทั้งหมดเป็นไม่ยินยอมได้
```sql
-- ดูว่ามีกี่คนที่ยังเป็น legacy (ยังไม่เคยถูกถามจริง)
SELECT count(*) FROM customers WHERE "marketingConsentSource" = 'legacy';
```

### 2. ✅ ระยะเวลาเก็บข้อมูล — เคาะและลงโค้ดแล้ว

- บัญชีลูกค้าและที่อยู่: **12 เดือน** หลังใช้บริการครั้งสุดท้าย
- ประวัติการสั่งและเอกสารบัญชี: **5 ปี**
- ข้อความแชต: **12 เดือน**

บังคับด้วย `prisma/pdpa-retention.ts` (cron ตี 4 ทุกวัน) · ตัวเลขอยู่ใน `src/modules/pdpa/retention.ts`
⚠️ **แก้ตัวเลขที่นั่นแล้วต้องแก้ในนโยบายที่เผยแพร่ด้วย** ไม่งั้นบอกลูกค้าอย่างทำอีกอย่าง

⚠️ ผลข้างเคียงที่ต้องบอกลูกค้า: **แต้มสะสมหมดอายุพร้อมบัญชี** เมื่อเงียบเกิน 12 เดือน
เขียนไว้ในนโยบายแล้ว ควรบอกซ้ำในเงื่อนไขโปรแกรมสะสมแต้ม

### 3. เติมข้อมูลกิจการในนโยบาย

ชื่อนิติบุคคล ที่อยู่ อีเมล เบอร์ติดต่อ และยืนยัน **region ของเซิร์ฟเวอร์ Hetzner** จากคอนโซล
(เอกสารเขียนไว้ว่าอยู่นอกประเทศไทย ต้องระบุประเทศให้ถูก)

## สิ่งที่ระบบทำถูกอยู่แล้ว (ไม่ต้องแก้)

- เบอร์โทรเข้ารหัสก่อนเก็บ และ API คืนแค่ 4 ตัวท้าย
- ลูกค้าปิดรับข่าวสารเองได้ และ broadcast หักคนที่ปฏิเสธออกทุกครั้ง
- ไม่เขียนชื่อ เบอร์ หรือที่อยู่ลง log ทั่วไป
- แยกสิทธิ์ตามหน้าที่ — ครัวเห็นที่อยู่แต่ไม่เห็นเบอร์ · คนตอบแชตไม่เห็นหน้าลูกค้าและรายงาน
- กันดูข้อมูลข้ามร้านทุก endpoint และมี e2e คุม
- การแก้ไขสำคัญโดยแอดมินถูกบันทึกใน `audit_logs`
- สำรองข้อมูลอัตโนมัติทุกวัน เก็บ 14 วัน
- **ลบข้อมูลตามระยะเวลาอัตโนมัติ** — dry-run เป็นค่าเริ่มต้น ต้องใส่ `--apply` ถึงลบจริง
- **ขอความยินยอมก่อนส่งการตลาด** และบันทึกว่ายินยอมเมื่อไร มาจากไหน
- **ถอนได้ 3 ทาง**: สวิตช์ในโปรไฟล์ · พิมพ์ "หยุดข่าวสาร" ใน LINE · แอดมินตั้งให้
- ทุก broadcast ต่อท้ายวิธีปฏิเสธอัตโนมัติ ไม่ขึ้นกับว่าคนเขียนจะจำใส่ไหม
- ลูกค้ากดขอลบข้อมูลเองได้จากหน้าโปรไฟล์ (เข้ากล่องแชตให้ร้านดำเนินการใน 30 วัน)
