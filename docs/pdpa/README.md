# PDPA pack — ชุดเอกสารคุ้มครองข้อมูลส่วนบุคคล

สถานะ: **ร่างครบ รอเจ้าของกิจการเติมข้อมูลและให้นักกฎหมายตรวจ** (9 ก.ย. 2026)

เอกสารชุดนี้เขียนจาก **โค้ดจริงของระบบ** ไม่ใช่แม่แบบทั่วไป ทุกข้อที่เขียนว่าระบบทำอะไรถูกตรวจกับ
`schema.prisma` และ module ที่เกี่ยวข้องแล้ว

| ไฟล์ | ใช้ทำอะไร | ใครอ่าน |
|---|---|---|
| `privacy-policy.md` | นโยบายที่ต้องเผยแพร่ให้ลูกค้าอ่าน | ลูกค้า (หลังเติมข้อมูลและตรวจแล้ว) |
| `consent-notices.md` | ข้อความขอความยินยอม + จุดที่ต้องวางในระบบ | คนทำ UI |
| `data-map.md` | เก็บอะไร ที่ไหน นานแค่ไหน ใครเห็น | เจ้าของ + คนดูแลระบบ |
| `data-subject-requests.md` | ขั้นตอนตอบคำขอ ขอดู/ขอแก้/ขอลบ | เจ้าของ + แอดมิน |

> ⚠️ **ผมไม่ใช่นักกฎหมาย** เอกสารนี้เป็นร่างที่ทำให้ทนายตรวจได้เร็วขึ้น ไม่ใช่ตัวแทนการตรวจโดยทนาย
> โดยเฉพาะข้อ "ระยะเวลาเก็บข้อมูล" และ "ฐานทางกฎหมาย" ควรให้ผู้รู้ยืนยัน

## ต้องตัดสินใจก่อนเปิดใช้จริง

### 1. ⚠️ การตลาดยังเป็นแบบ "ส่งได้จนกว่าจะปฏิเสธ" — ต้องเคาะก่อนยิง broadcast ชุดแรก

ตอนนี้ `customers.marketingOptedOut` ค่าเริ่มต้นคือ `false` แปลว่าลูกค้าใหม่ทุกคน **ถูกถือว่ายอมรับข่าวสารทันที**
PDPA มาตรา 19 ให้การตลาดทางตรงต้องได้ความยินยอม **ก่อน** ส่ง

| ทางเลือก | ผลกับธุรกิจ | งานที่ต้องทำ |
|---|---|---|
| **ก. เปลี่ยนเป็นขอก่อน (opt-in)** — ปลอดภัยที่สุด | ลูกค้าเดิมทั้งหมดจะไม่ได้รับ broadcast จนกว่าจะกดยอมรับ · reach ตกทันที | migration เปลี่ยนค่าเริ่มต้น + หน้าถามความยินยอม + เก็บวันที่ยินยอม (~4 ชม.) |
| **ข. ขอเฉพาะลูกค้าใหม่ ลูกค้าเดิมส่งขอความยินยอม 1 ครั้ง** | เสีย reach เฉพาะคนที่ไม่ตอบ | เท่ากับ ก. + broadcast ขอความยินยอม 1 รอบ |
| **ค. คงไว้แบบเดิม** | เสี่ยงถูกร้องเรียน/ปรับ | ไม่ต้องทำอะไร แต่ **ไม่แนะนำ** |

ผมแนะนำ **ข.** เพราะรักษาฐานลูกค้าเดิมไว้ได้บ้างและถูกกฎหมาย · **ยังไม่ได้แก้โค้ด รอคุณเคาะ**

### 2. ระยะเวลาเก็บข้อมูล — ยังไม่มีตัวเลข และยังไม่มีการลบอัตโนมัติ

นโยบายมีช่องว่างให้เติม 3 จุด แนะนำค่าเริ่มต้นที่ร้านอาหารส่วนใหญ่ใช้

- บัญชีลูกค้าและที่อยู่: 12 เดือนหลังใช้บริการครั้งสุดท้าย
- ประวัติการสั่งและเอกสารบัญชี: 5 ปี (ตามกฎหมายบัญชี)
- ข้อความแชต: 12 เดือน

⚠️ เคาะแล้วยัง **ไม่มีโค้ดลบอัตโนมัติ** ต้องเขียน job เพิ่ม (~3 ชม.) ไม่งั้นนโยบายกับความจริงไม่ตรงกัน

### 3. เติมข้อมูลกิจการในนโยบาย

ชื่อนิติบุคคล ที่อยู่ อีเมล เบอร์ติดต่อ และยืนยัน **region ของเซิร์ฟเวอร์ Hetzner** จากคอนโซล
(เอกสารเขียนไว้ว่าอยู่นอกประเทศไทย ต้องระบุประเทศให้ถูก)

## เช็คลิสต์ก่อนเก็บข้อมูลลูกค้าจริง

- [ ] เติมข้อมูลในวงเล็บเหลี่ยมใน `privacy-policy.md` ให้ครบ
- [ ] เคาะข้อ 1 (opt-in) และข้อ 2 (ระยะเวลาเก็บ) ข้างบน
- [ ] ให้นักกฎหมายหรือที่ปรึกษา PDPA ตรวจ
- [ ] เผยแพร่นโยบายเป็นหน้าเว็บสาธารณะ
- [ ] ตั้ง `VITE_PRIVACY_URL` แล้ว build LIFF ใหม่ → ลิงก์ในหน้าโปรไฟล์จะโผล่เอง
- [ ] ใส่ลิงก์นโยบายในข้อความต้อนรับของ LINE OA
- [ ] ต่อท้ายทุก broadcast ด้วยวิธีปฏิเสธการรับข่าวสาร
- [ ] ซ้อมขั้นตอนขอลบข้อมูลใน `data-subject-requests.md` กับข้อมูลทดสอบ 1 รอบ

## สิ่งที่ระบบทำถูกอยู่แล้ว (ไม่ต้องแก้)

- เบอร์โทรเข้ารหัสก่อนเก็บ และ API คืนแค่ 4 ตัวท้าย
- ลูกค้าปิดรับข่าวสารเองได้ และ broadcast หักคนที่ปฏิเสธออกทุกครั้ง
- ไม่เขียนชื่อ เบอร์ หรือที่อยู่ลง log ทั่วไป
- แยกสิทธิ์ตามหน้าที่ — ครัวเห็นที่อยู่แต่ไม่เห็นเบอร์ · คนตอบแชตไม่เห็นหน้าลูกค้าและรายงาน
- กันดูข้อมูลข้ามร้านทุก endpoint และมี e2e คุม
- การแก้ไขสำคัญโดยแอดมินถูกบันทึกใน `audit_logs`
- สำรองข้อมูลอัตโนมัติทุกวัน เก็บ 14 วัน
